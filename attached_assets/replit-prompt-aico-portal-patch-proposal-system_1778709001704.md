# Project Patch: The Proposal System

You are patching the AICo Atelier app (v1 + v2) to upgrade its proposal generation, case study pipeline, timeline visualization, and team bios surfaces. This patch is invariant to whether v3 has shipped: it consumes v3 data when present and falls back to manual entry when absent.

Inherit all non-negotiable principles from v1 + v2: agents prepare, humans commit; show the work; source-grounded; partner authority lock; immutable audit; bilingual-aware; watermark synthetic data.

## 1. Proposal default output format — HTML first

### 1.1 Change

The Proposal Composer's default output format becomes **HTML**, rendered with the same brand system as the public AICo / Maven AI website and the Tasama / Dogan POVs. DOCX and PDF remain available as **export** options, not default.

### 1.2 Why

- HTML proposals match the firm's voice: senior, modern, interactive — a differentiator vs. Tier-1 PowerPoint/PDF submissions.
- An HTML proposal can carry the interactive timeline (§4) and the team bios grid (§5) natively; DOCX cannot.
- Same brand system as the website means the firm's identity is consistent across every artifact.
- HTML is also more accessible (WCAG 2.2 AA enforceable) and easier to update / version inline.

### 1.3 HTML proposal structure (the standard sections)

Every AICo HTML proposal renders these **sections in this order**, with a sticky left-rail TOC and section anchors for navigation. Sections marked `(optional)` are omitted unless the opportunity has the relevant content.

| # | Section ID | Section Name | Drafted by |
|---|---|---|---|
| 0 | `cover` | Cover (client name, proposal title, date, version, "Confidential — for [Client]") | Composer |
| 1 | `executive-summary` | Executive Summary | Composer (Opus 4.6 polish) |
| 2 | `company-profile` | Company Profile (AICo at a glance) | Brand Profile Writer (sub-agent) |
| 3 | `understanding` | Our Understanding of Your Challenge | Context Writer |
| 4 | `pov` | Our Point of View | POV Author (reused) |
| 5 | `approach` | Approach and Methodology | Approach Writer |
| 6 | `workplan` | Work Plan (renders the **Interactive Timeline** — §4) | Workplan Writer + Timeline Composer |
| 7 | `deliverables` | Deliverables and Milestones | Workplan Writer |
| 8 | `value-case` | Value Case (baseline → target) | Value Case Tracker (reused) |
| 9 | `team` | The Team (renders the **Team Bios** grid — §5) | Bio Crafter (sub-agent) |
| 10 | `case-studies` | Relevant Case Studies (renders 3 sanitized 1-pagers — §3) | Case Study Picker + Composer |
| 11 | `commercials` | Commercials and Pricing | Pricing Strategist (reused from v2) |
| 12 | `terms` | Terms and Conditions | Terms & Risk Writer |
| 13 | `compliance` `(optional)` | RFP Compliance Matrix | Compliance Reviewer |
| 14 | `appendices` `(optional)` | Appendices | Composer |

The Composer orchestrates the sub-agents in parallel where possible (Sections 1–10 fan out; Section 11 waits for Section 6 to lock; Sections 12–14 follow Section 11).

### 1.4 HTML proposal layout signatures

Mirror the Tasama / Dogan POV pattern with proposal-specific additions:

- **Sticky left rail (220 px wide)** — TOC with section anchors; current section highlighted in gold; scroll-spy. Collapsible on narrow viewports.
- **Sticky top bar (56 px)** — client name + proposal title + version + "Confidential" badge + language toggle (EN | عربي) + export buttons (DOCX / PDF).
- **Main scroll body** — sections rendered full-bleed with `scroll-snap-type: y proximity`. Each section opens with the standard eyebrow → headline → italic accent → 2px gold-left-border lede pattern from the website.
- **Per-section gold rule** — a 1px gold divider at the bottom of each section, mirroring the website.
- **Print stylesheet** — when the user prints or exports to PDF, the sticky elements collapse; each section becomes a print page with a header (client name) and footer (page X of Y + "Confidential — for [Client]").
- **Per-user watermark** — when the proposal is shared as a URL (default for HTML proposals), the page renders a low-opacity diagonal watermark with the recipient's name + email + timestamp. Inherited from v2's Publish Sentinel pattern.

### 1.5 HTML proposal as a shareable artifact

Proposals can be:

1. **Exported** as a self-contained HTML file (single file with inlined CSS/SVG, no JS dependencies needed for static viewing — interactive timeline degrades to a static SVG when offline).
2. **Hosted** at a per-proposal URL inside the Salon (auth-gated, watermarked, expiring access). Use this by default; export only for procurement-required submission.
3. **Exported to DOCX or PDF** as a faithful flattening (no timeline interactivity; team bios as a static grid).

### 1.6 Replace v1 §8.4.3 Proposal Composer output schema

The output of the Proposal Composer becomes:

```ts
ProposalOutput {
  proposal_id, version,
  format: 'html'|'docx'|'pdf',          // default 'html'
  html_url?,                             // Salon-hosted, watermarked
  html_file_id?,                         // self-contained export
  docx_file_id?, pdf_file_id?,
  sections: ProposalSection[],
  toc: { id, label, level }[],
  embedded_components: {
    timeline_id?,                        // Interactive Timeline (§4)
    bio_grid_id?,                        // Team Bios grid (§5)
    case_study_ids: string[]             // §3
  },
  pricing_model_id,
  win_themes_inserted[],
  compliance_matrix?
}
```

## 2. Company Profile section — new sub-agent

### 2.1 Brand Profile Writer (new sub-agent of Proposal Composer)

**Purpose.** Render the Company Profile section using a single firm-wide source of truth. The firm profile is parameterized so every proposal stays consistent and updatable in one place.

**Inputs.** `{ proposal_id, audience: { buyer_persona, sector }, length: 'compact'|'standard'|'long' }`

**Output.** A rendered HTML block covering: firm at a glance (founding, geography, focus, partners), the four offerings (lifted from the website), the four levers (lifted from the website), credentials snapshot (count of engagements, sectors served, public testimonials count), and platform alliances (cloud + tooling certifications — pulls from v5 Certification Tracker if present, manual otherwise).

**Source of truth.** A single `firm_profile` record in the database, edited at `/atelier/firm-profile`. Versioned. Every proposal records the firm-profile version used.

**Guardrails.** No invented facts. Every claim is sourced — either to the firm-profile record (internal) or to a public artifact (the website's `/about`, a credential, a published testimonial).

**Model.** Sonnet 4.6.

## 3. Case Study pipeline — two new agents

### 3.1 The problem this solves

The v1 Case Study Picker assumes that case-study 1-pagers already exist in the Atelier. They don't, because v1 has no production pipeline from a *completed engagement's deliverables* to a *publishable, sanitized 1-page case study*. This patch adds the pipeline.

### 3.2 New agent — Case Study Composer

- **Purpose:** From a completed engagement's deliverables + value case + decisions log, produce a 1-page case study in AICo's HTML template — with a structured, sanitized, citation-bound narrative.
- **When it runs:** Auto-triggered at the engagement's Compound stage gate, by the Atelier Curator. Also runnable on demand from the engagement workspace.
- **Inputs:** `{ engagement_id, naming_mode: 'named'|'anonymized'|'sector_only', target_length: '1_page'|'2_page', emphasis?: 'agentic_ai'|'legacy_modernization'|'data_foundations'|'ai_product' }`
- **Output:** `{ case_study_html, case_study_docx, structured_record: { headline, sector, client_signal, problem, approach, outcome, value_quantified, named_team[], consent_state }, citations[], sanitization_report_id }`
- **Sub-agents (chained):**
  1. **Deliverable Harvester** — reads the engagement's deliverables, charter, value case, decisions log, RAID closeouts, and Synthesis-Critic-approved final artifacts; extracts the story arc (challenge → approach → outcome).
  2. **Sanitization Sentinel** — passes the harvested content through the sanitization rules (§3.3) and produces a `sanitization_report`.
  3. **Outcome Quantifier** — pulls the value case's realized numbers; produces 2–3 quantified outcome statements (e.g., "Reduced complaint cycle time by 68% within 12 weeks").
  4. **Case Study Stylist** — renders the sanitized story arc into the AICo 1-page HTML case study template.
- **Tools:** `engagements.read`, `deliverables.read`, `value_case.read`, `decisions.read`, `dlp.scan`, `knowledge.search` (comparable case studies), `html.generate`.
- **Model:** Sonnet 4.6 for narrative; Haiku 4.5 for sanitization; Opus 4.6 for synthesis on demand.
- **Human checkpoints:**
  1. Engagement Lead reviews the sanitized draft.
  2. Partner approves naming mode (named requires client consent — pulled from the Consent Steward record in v4 if present; manual confirmation otherwise).
  3. Atelier Curator promotes to the credentials library.
- **Guardrails:**
  - Naming mode `named` requires an active client consent record. Without consent, default to `sector_only`.
  - Sanitization Sentinel pass must be GREEN; any RED flag blocks promotion.
  - Quantified outcomes must reference the value case ID; no hand-waved numbers.
- **Evals:** Golden case studies (Tasama BPO, DGE Effortless, Aldrees BOQ); measure: sanitization precision, outcome accuracy, partner-acceptance rate.

### 3.3 New agent — Sanitization Sentinel

- **Purpose:** Read a draft case study (or any internal artifact intended for external publication) and detect / redact client-sensitive content.
- **When it runs:** As a sub-agent of the Case Study Composer; also runnable standalone on any artifact heading to public publication (thought leadership, website credentials, partner-firm proposals).
- **Inputs:** `{ artifact_id, naming_mode, target_audience: 'public'|'partner_firm'|'client_panel' }`
- **Output:** `{ sanitization_report: { findings[]: { kind, severity, location_anchor, original_text, proposed_replacement, rationale }, residual_risk: 'green'|'amber'|'red', overall_recommendation }, sanitized_artifact_html }`
- **Detection rules (configurable; defaults below):**
  - **Client identity** — client name → "a leading GCC public sector entity" (or sector_only / named per the mode).
  - **Personal names** — internal client staff names → role + sector (e.g., "Director of CX at a federal entity").
  - **System names** — proprietary product names → generic system family (e.g., "the entity's customer service platform").
  - **Real ID patterns** — passport numbers, Emirates ID, national ID, bank IBANs → fully redacted.
  - **Real financial figures** — actual revenue figures, exact deal sizes, line-item budgets → ranges (e.g., "$50–$100M").
  - **Internal codenames** — engagement code names → none, or AICo-side code only.
  - **Real dates** — exact engagement dates → quarter (e.g., "Q3 2025") unless naming mode is named and consent exists.
  - **Sector-specific sensitivities** — defense / intelligence / sovereign work — never includes the underlying system or scope; blocked unless Partner override with rationale.
- **Tools:** `dlp.scan` (rule-based; pgvector embedding match for codename variants; configurable rule library at `/atelier/sanitization-rules`), `knowledge.search` (prior client sensitivities), `regex.match`.
- **Model:** Haiku 4.5 (volume); escalate to Sonnet 4.6 if amber findings need synthesis.
- **Human checkpoints:** Engagement Lead approves the proposed replacements; Partner reviews any AMBER residual risk; RED blocks publication.
- **Guardrails:**
  - Sentinel never publishes — it only redacts and proposes; humans approve.
  - Detection rules are versioned; every sanitization run records the rule version used.
  - Override of a RED finding requires Partner + a written rationale logged to audit.
- **Evals:** Seeded artifacts with planted sensitive patterns (Emirates ID, named internal staff, real revenue, codename variants); measure precision / recall against the truth labels.

### 3.4 Patch to v1 Case Study Picker

Previously the Picker assumed a manually-curated library. Update its retrieval to query the Atelier's case study library where `consent_state` and `sanitization_report.residual_risk = 'green'`. The Picker ranks by relevance (sector × buyer-persona × offering anchor) and pulls **two named** + **one sector-only** by default, or three sector-only if no consent exists.

### 3.5 Case Study 1-page HTML template

The 1-page HTML case study template renders with the AICo brand system:

```
[Eyebrow: CASE STUDY · {SECTOR} · {QUARTER YEAR}]
{Headline — single sentence outcome, italic accent on the verb}

The challenge ── (90 words; problem statement; client signal — sector-tagged if anonymized)
Our move      ── (90 words; approach + offering anchor + agentic pattern used)
The outcome   ── (60 words + a 3-tile quantified outcome strip: metric · delta · timeframe)

Team          ── (named partners + principals; partner-firm staff if any, attributed)
Period        ── (start → end, anonymized to quarter if no naming consent)
Stack         ── (chips: cloud, model family, tools — at brand level, not specific versions)

Footer        ── (Confidential · {NAMING MODE} · Sanitization rule library vN.x)
```

The template is responsive and prints to a single A4 page. A 2-page variant exists for engagements with deeper outcomes.

## 4. Interactive Timeline component — new reusable component

### 4.1 What it is

A first-class React component (`<InteractiveTimeline />`) that visualizes an engagement's plan or actual state across **phases × workstreams × milestones × deliverables**, with click-to-drill-down on every node.

### 4.2 Where it's used

| Surface | Data shown | Mode |
|---|---|---|
| Proposal Workplan section | The **proposed** timeline | read-only, illustrative |
| Engagement Workplan tab | The **current** timeline (plan vs. actual) | live, interactive |
| Salon Workplan tab | The **client-visible** subset of the timeline | read-only, watermarked |
| Atelier Curator harvest | Frozen at engagement closeout | read-only, archival |

### 4.3 Visual structure

- Horizontal time axis spanning the engagement duration.
- Phases as horizontal bands (e.g., **Diagnose → Design → Build → Adopt → Compound**), color-coded with the AICo gold gradient ramp from `--gold-deep` to `--gold-soft`.
- Workstreams as swim lanes within phases (e.g., **Data foundation**, **Agentic platform**, **Adoption**, **Governance**).
- Milestones as gold-rimmed circular nodes.
- Deliverables as smaller gold-filled diamond nodes anchored to their owning milestone.
- Today line as a thin gold vertical rule.
- For live mode, plan track (dashed) overlays the actual track (solid).

### 4.4 Drill-down

Every node is clickable. Clicking opens a right-rail drawer with:

- **Milestone** drill-down: objective, success criteria, deliverable list, decisions required from client, named owner, planned date, actual date, status (GREEN/AMBER/RED), dependencies, RAID items linked, agent runs linked.
- **Deliverable** drill-down: latest version, Synthesis Critic readiness, citations count, approval state, link to the deliverable workspace.
- **Phase** drill-down: phase objective, success metric, workstreams, % complete, named phase lead.

In the proposal mode, drill-down is **read-only**: it shows the **proposed** content (deliverable names, milestone objectives, dates) without exposing live engagement data.

### 4.5 Data model

The timeline is computed from existing entities (no new tables required):

- `Engagement.charter.success_metrics` → phase success metrics.
- `Engagement.workstreams[]` → swim lanes.
- `Deliverables` → diamond nodes.
- `RaidItems` linked to milestones → AMBER/RED chip overlays.
- `AgentRuns` linked to deliverables → activity badges on hover.

For **proposal mode**, the timeline reads from a `proposed_workplan` jsonb on the opportunity (drafted by the Workplan Writer sub-agent). This proposed_workplan is the seed that, on signature, becomes the live engagement workplan.

### 4.6 New sub-agent — Timeline Composer

- **Purpose:** From the engagement's workplan (or the proposal's proposed_workplan), produce the structured timeline data and render notes.
- **Inputs:** `{ engagement_or_opportunity_id, mode: 'proposed'|'live'|'archival', client_visibility?: 'full'|'salon_filtered' }`
- **Output:** `{ phases[], workstreams[], milestones[], deliverables[], today_anchor, render_notes }`
- **Tools:** `engagements.read`, `opportunities.read`, `workplan.read`, `raid.read`, `deliverables.read`.
- **Model:** Haiku 4.5.
- **Guardrails:** In `salon_filtered` mode, redact internal-only milestones and deliverables; never expose AICo's internal hypothesis-tree branches.
- **Human checkpoints:** Engagement Lead reviews the proposed timeline in proposal mode before submission; Partner reviews the Salon-filtered view before each client publish.

### 4.7 Bilingual / RTL

Component renders RTL when language is AR. Phase order reverses; the today line + all text mirror.

### 4.8 Static fallback for export

When the proposal is exported as PDF / DOCX, the timeline renders as a high-fidelity SVG with the milestone list as a structured table beneath it. Drill-down content moves to footnotes / endnotes per milestone.

## 5. Team Bios — deep specification

### 5.1 What changes

The v1 §8.4.3 "Team & Bios Writer" was named but not deep-specced. Replace it with **Bio Crafter** — a first-class sub-agent with a clear data model and rendering spec.

### 5.2 The three worker types in a proposal team

When v3 has shipped:
- **Employees (FTE)** — named, photographed, full bio. Role on engagement explicit.
- **Contractors** — named (with consent) or labeled "AICo Associate"; bio with photo if consented. Role on engagement explicit.
- **Partner-Firm Resources** — named with explicit partner-firm attribution ("Karim — Senior Engineer, BGTS (partner firm)"). Photo permitted with partner-firm consent. Role on engagement explicit. Includes the partner firm's logo next to the person's name.

When v3 has not yet shipped (early state), bios fall back to a manually maintained `proposal_personnel` table with the same fields; the Bio Crafter populates from there. Forward-compatible.

### 5.3 New sub-agent — Bio Crafter

- **Purpose:** From the engagement-proposed team list, render a Team section with one bio per person, drawing from the Roster + Skill graph + engagement history + certifications, written in the proposal's voice for the named buyer.
- **Inputs:** `{ proposal_id, proposed_team[]: { person_id?, partner_firm_id?, manual_record_id?, role_on_engagement, allocation_pct }, audience: { buyer_persona, sector }, sensitivity_mode: 'anonymized_clients'|'named_clients' }`
- **Output:** `{ team_section_html, bios[]: { person_id, role_on_engagement, name, title, photo_url, summary_md, credentials[], certifications[], languages[] } }`
- **Data sources:**
  1. Roster — name, title, photo, contracting entity, partner-firm.
  2. Skill graph — top 5 skills relevant to this engagement.
  3. Engagement history — last 3 relevant engagements (sanitized by the Sanitization Sentinel per `sensitivity_mode`).
  4. Certifications — platform and methodology certifications.
  5. Languages — for client-facing role match (Arabic-fluent flag is important in GCC).
- **Rendering:**
  - Grid of bio cards. Each card: square photo (or initials avatar if no photo / consent), name, title, role on engagement chip, 3-line summary, 3 credential pills (sanitized), 3 certification pills, language pills, partner-firm logo (if applicable).
  - Hover state reveals the next paragraph of bio and the LinkedIn icon (links out — internal only).
  - Click opens a full-bio modal with a longer narrative + the full credential list.
- **Tools:** `roster.read`, `skills.read`, `engagement_history.read`, `certifications.read`, `dlp.scan` (sanitization), `knowledge.search` (comparable bios for tone).
- **Model:** Sonnet 4.6 for the narrative; Haiku 4.5 for the cards.
- **Guardrails:**
  - Cannot include a person without confirming they are assigned (Access Sentinel check from v3 if present).
  - Partner-firm bios cannot omit the partner-firm attribution.
  - In `anonymized_clients` mode, all client references in past credentials are sanitized.
  - No comp data, no internal day rates, ever.
- **Human checkpoints:**
  - Engagement Lead reviews the team list before bios are drafted.
  - Each person reviews and approves their own bio (Roster integration — a notification fires when a bio is drafted that includes them).
  - Partner approves the final Team section.
- **Evals:** Golden team grids; measure: bio accuracy (claims match Skill graph + history), tone match to firm voice, partner-acceptance rate.

### 5.4 Patch to The Roster (v3)

Add a `bio_consent` record per person:

```ts
BioConsent {
  person_id,
  photo_consent,                       // bool
  named_consent,                       // bool  (otherwise default to initials avatar)
  named_clients_in_history_consent,    // bool  (otherwise sector-only descriptions)
  last_reviewed_at,
  last_reviewed_by
}
```

The Bio Crafter respects these consents on every render. Consent is renewed at every annual review.

## 8. MVP scope for this patch (what ships)

A reviewer should be able to:

1. Generate a proposal for the seeded Tasama opportunity and see an HTML proposal with all 12 standard sections (plus Compliance Matrix if RFP is loaded). The HTML opens at a Salon-hosted URL, watermarked.
2. Click any milestone in the proposal's Workplan section and see a drill-down drawer with the milestone's objective, named owner, deliverable list, and success criteria.
3. From the proposal's Team section, click any bio card and see a full-bio modal with sanitized client names and 5 relevant credentials.
4. Close a seeded engagement to its Compound stage and have the Case Study Composer auto-run; receive a sanitized 1-page HTML case study; approve the sanitization findings; promote to the credentials library.
5. Plant a sensitive pattern (real Emirates ID, real revenue figure, internal codename) in a case study draft and watch the Sanitization Sentinel detect, propose replacements, and block publication until cleared.
6. Switch the proposal to AR; verify the Workplan timeline and Team grid render RTL with mirrored text and reversed phase order.
7. Export the proposal as PDF; verify the timeline renders as a high-fidelity SVG with a structured milestone table beneath; verify the team grid renders as a static grid; verify the print stylesheet places confidentiality + watermark on every page.
8. Open `/atelier/credentials` and see the newly generated case study with `consent_state` and `naming_mode` chips; click into it to see the structured record + the sanitization report.

### Non-functional requirements

- HTML proposal first load < 2s for a 25-section proposal.
- Timeline render < 500ms for up to 100 nodes.
- Case Study Composer end-to-end run < 90s for a typical engagement.
- Sanitization Sentinel precision ≥ 0.95 on the seed test set; recall ≥ 0.90.
- AR / EN parity on every component.

### Out of scope for this patch

- Live co-editing of proposal HTML (deferred — proposal authoring is single-cursor in v1/v2; co-editing is a later add).
- Direct e-signature on the proposal (lives in v4's Codex module).
- ML-based sanitization (rule-based + pgvector match is the v1 of this; ML escalation is v4).
- Cross-firm case study syndication (sharing sanitized cases with partner firms BGTS / Thoughtworks / Mobven — v5).
