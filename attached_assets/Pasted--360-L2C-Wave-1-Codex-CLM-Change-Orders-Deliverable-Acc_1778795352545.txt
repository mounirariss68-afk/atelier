#360 - L2C Wave 1 — Codex (CLM), Change Orders, Deliverable Acceptance

What & Why

Wave 1 of the Lead-to-Cash roadmap (artifacts/atelier/docs/prd/lead-to-cash-gap-analysis.md §E, gaps G01 + G02) makes the contract a first-class portal artifact and lays the cross-cutting foundations every later wave needs:

Codex — clause library, contract instruments (MSA / SOW / NDA / DPA / change order / side letter), version chain, two-partner countersign, e-sign dispatch (DocuSign + Tabellio for KSA), DPA gating, renewal watcher.
Change orders — first-class in-portal scope/rate/term/team change motion with partner approval and client countersign, replacing today's RAID-as-change-order workaround.
Deliverable Acceptance — a client-signed attestation that a milestone is complete. This is the seam between delivery and revenue — Wave 2 milestone-based revrec keys off these acceptance records, Wave 3 milestone invoicing keys off the same.
Without this wave, the rest of the roadmap has nothing to anchor to: revrec needs contract_value + recognition_method; invoicing needs the bill-to entity + tax jurisdiction + signed-line basis; renewals need the term end-date; cash forecast needs scheduled-milestone amounts. v4 §6.A spec'd Codex first for this reason and we mirror that ordering exactly.

Done looks like

Operational (what a partner / finance user can do that they cannot do today)

A Partner can compose an SOW from an opportunity, generate a draft from clause-library templates, request internal review, get the two-partner countersign to clear, and dispatch the envelope to DocuSign (or Tabellio for KSA) — all from /codex/contracts/:id.
A Senior Manager can propose a scope change order on /engagements/:id; a Partner can approve it; the system dispatches the change order to the client for countersign; the engagement charter shows the new committed scope after acceptance.
A Senior Manager can submit a Deliverable Acceptance Form to a client from the engagement Deliverables tab; Finance can record the returned client signature (PDF + signer name + date); the acceptance is bound to a milestone and visible in audit.
The DPA Sentinel agent flags any engagement with regulated data classes that lacks an active DPA and surfaces it on the partner cockpit.
The Renewal Watchdog agent runs daily and lists every contract within 90 / 60 / 30 days of expiry.
Data + audit

Every salesStage=contract opportunity carries a real atelier_contract row (back-fill migration for existing demo data).
Every state transition on contract / change order / deliverable acceptance is append-only logged in atelier_audit_log and rendered as an audit_timeline card.
All restricted personas (contractor, partner_firm_resource, recruiter) are denied on every new write and on every individual contract / change-order / acceptance read; firm-wide RLS map matches §C.3 of the L2C doc.
Quality

All capabilities (listed under Steps 8) have ≥2 representative prompts and a smoke fixture in artifacts/api-server/tests/cli-smoke/run.ts.
Restricted-set deny gate added to capabilitiesForPersona() so contractor / partner_firm_resource / recruiter cannot reach any outboundChannel: "email" capability.
Migration applied; canonical seed plants 3 sample contracts (1 MSA, 1 SOW, 1 change order — accepted), 12 sample clauses, 1 DPA, 1 deliverable acceptance.
Out of scope

Revenue schedule / period postings (Wave 2, #361).
Invoice generation / e-invoicing / AR / dunning (Wave 3).
Cash application / bank rec / cash forecast / renewal-opportunity opening (Wave 4 — note the Renewal Watchdog agent ships in this wave; the renewal_open_opportunity capability ships in Wave 4 to avoid stranded UX).
Public client portal for clients to sign in-portal (v6+) — Wave 1 dispatches to DocuSign / Tabellio and accepts a returned signed PDF.
Async-video reference interviews (deferred to v5 per v4 §3).
Embedded redline editor — Redline Analyst produces a clause-by-clause diff report in Wave 1; in-portal redline editing is a v6 stretch.

Architectural constraints

State machines are enforced server-side, not client-side. Frontend reads validNextStates from the API per record.
Two-partner countersign is a hard gate — no API path bypasses it (per v4 Resolution 6). E-sign adapters refuse to dispatch without two_partner_countersigned = true.
Outbound channels — only dunning_send_reminder (Wave 3) carries outboundChannel: "email" per the L2C doc; Wave 1 contract / change-order dispatch routes through DocuSign / Tabellio adapter (server-to-server), so outboundChannel: null and the catalog records the side effect via irreversible: true.
Renewal Watchdog is a daemon with a per-engagement cost cap and a run-log entry per execution (per v4 Resolution 7 + 10) — bound to input-evidence (the AR + contract snapshot it ran on), not output-evidence.
No new top-nav entry except /codex. All finance surfaces in Waves 2–4 mount under /wallet sub-nav.
Integrations / secrets needed

DocuSign (via Replit Integrations if available; otherwise env vars DOCUSIGN_INTEGRATION_KEY, DOCUSIGN_USER_ID, DOCUSIGN_ACCOUNT_ID, DOCUSIGN_BASE_URL). Use sandbox account in dev.
Tabellio (KSA) — env vars TABELLIO_API_KEY, TABELLIO_ENV. Stub adapter if no live account; tests use the stub.
Email channel reuses the existing transactional path; no new SMTP credentials needed.
