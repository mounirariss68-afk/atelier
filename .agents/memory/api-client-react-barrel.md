# Exposing a new orval hook to atelier/maven frontends

After adding a path+operation to `lib/api-spec/openapi.yaml` and running
`pnpm --filter @workspace/api-spec codegen`, orval rewrites
`lib/api-client-react/src/generated/api.ts` (hooks) and
`generated/api.schemas.ts` (types) — but the hook still errors with TS2724
"no exported member" when imported from `@workspace/api-client-react`.

Two manual steps are required:

1. **Add it to the barrel.** `lib/api-client-react/src/index.ts` re-exports an
   **explicit named list** from `./generated/api` (NOT `export *`) and is NOT
   regenerated by orval. New hooks must be appended by hand, mirroring an
   existing entry: for a query endpoint add `getXUrl, getXQueryKey,
   getXQueryOptions, useX`; for a mutation add `getXUrl, getXMutationOptions,
   useX`. (Schemas/types ARE covered by `export * from "./generated/api.schemas"`,
   so input/candidate *types* resolve even when the hook doesn't — that
   mismatch is the tell.)

2. **Rebuild the declaration output.** Consumers resolve `@workspace/api-client-react`
   through TS **project references** → its emitted `.d.ts` in `dist`
   (composite + emitDeclarationOnly), NOT the `src` the `exports` field points
   at for runtime. Run `tsc -b lib/api-client-react/tsconfig.json --force`.

**Why:** codegen chains `tsc --build` (`typecheck:libs`) which can abort on a
PRE-EXISTING error elsewhere (e.g. `lib/agents/src/registry.ts` "Wallet" not
assignable to AgentGroup) before emitting api-client-react's declarations,
leaving stale `.d.ts`. The frontend then typechecks against the old surface.

**How to apply:** whenever you add an endpoint and the frontend can't see the
hook, do both steps. The stale-declaration symptom is "type imports work, hook
import fails."
